# 6. Presentation of Results, Analysis, and Interpretation

## 6.1 System Implementation Results

### 6.1.1 Backend API Implementation

The MDSystem backend was successfully implemented as a **dual-server Express 5 application** running two independent processes from a shared codebase:

| Metric | Result |
|---|---|
| **GraphQL Endpoints** | 12+ GraphQL endpoints across EMR, Profile, Appointments, Consultations, Health Chat, Inventory (3 sub-modules), Prescriptions, Role Management, and Dashboard |
| **REST Endpoints** | 10+ REST route modules covering Authentication, Media, Analytics, Documents, Settings, Staff Management, Info/Announcements, and Consent |
| **Database Tables** | 60+ PostgreSQL tables with 40+ custom enum types |
| **Permission Keys** | 40+ granular permission keys across 11 functional modules |
| **Analytics Queries** | 30+ configurable statistical queries with multi-format export |
| **Socket.IO Event Types** | 15+ real-time event types across health chat, appointments, inventory, EMR updates, and administrative notifications |
| **Email Job Types** | 5+ email types (verification, 2FA OTP, password reset, notification, admin transfer) processed via BullMQ |

**Key Technical Achievements:**
- Raw parameterized SQL throughout (no ORM) with controlled FK/unique constraint handling via `queryControlled()`
- JWT dual-token architecture with staff session anchoring (`sid` validated per request)
- RFC 6238 TOTP implementation using pure Node.js `crypto` (no external TOTP library)
- Socket.IO Redis adapter enabling cross-server event delivery between port 3000 and 3001
- WHO ICD-11 API integration with local PostgreSQL caching and staleness detection
- Adaptive reCAPTCHA with HMAC shared-secret bypass for mobile apps
- Cryptographically random timing delays on authentication failures to prevent timing attacks

## 6.4 Architecture Analysis

### 6.4.1 Dual-Server Architecture Benefits

The decision to run two Express 5 server instances from a shared codebase (rather than a monolithic single server or separate codebases) yielded several advantages:

1. **Security Isolation:** Patient and staff API surfaces are exposed on separate ports with distinct JWT role enforcement, preventing accidental cross-role data exposure.
2. **Independent Scaling:** Under high patient load (e.g., semester-start appointment booking), the patient server can be scaled independently without affecting staff operations.
3. **Code Reuse:** All configuration, database connections, middleware, utilities, and business logic services are shared — eliminating code duplication between patient and staff APIs.
4. **Deployment Flexibility:** Each server can be restarted independently during maintenance; a staff server restart does not affect patient access.

### 6.4.2 GraphQL as Primary API Protocol

Using GraphQL (rather than pure REST) for CRUD-heavy modules provided:

1. **Reduced Round Trips:** The patient record viewer fetches 14+ data types in a single GraphQL request, compared to 14+ separate REST calls.
2. **Client-Driven Data Fetching:** Frontend components request exactly the fields they need, reducing over-fetching.
3. **Strong Typing:** `.graphql` schema files serve as living API documentation and enable IDE autocompletion.
4. **Flexible Filtering:** GraphQL resolvers handle complex filtering (status, date range, branch) without proliferating REST query parameters.

### 6.4.3 Raw SQL vs. ORM Trade-off

The decision to use raw parameterized SQL (via `pg`) without an ORM introduced trade-offs:

| Advantage | Description |
|---|---|
| Full query control | Complex multi-table joins, CTEs, and window functions for analytics |
| PostgreSQL-native features | Direct use of custom enums, JSONB, array types without ORM mapping |
| Performance transparency | No hidden N+1 queries or lazy-loading pitfalls |
| Reduced dependency surface | No ORM upgrade compatibility issues |

| Trade-off | Mitigation |
|---|---|
| No automatic migration generation | Manual SQL migrations with version-controlled `.sql` files |
| Verbose query writing | Centralized `query()` and `queryControlled()` helpers |
| No entity relationship mapping | Well-documented foreign key relationships in schema |

### 6.4.4 Shared Core Package Effectiveness

The `@mdsystem/core` factory pattern successfully enabled code reuse across three fundamentally different runtime environments:

| Capability | Web (localStorage/window) | Mobile (AsyncStorage/callback) |
|---|---|---|
| Token Storage | `localStorage.getItem('patient_accessToken')` | `AsyncStorage.getItem('patient_accessToken')` |
| Navigation on Logout | `window.location.assign('/auth/login')` | Session-expired callback → AuthContext state change |
| API Base URL | `''` (relative, proxied by Vite) | `https://www.mdsystemtip.space` (absolute) |
| Request Logging | Auto-enabled on `localhost` | Auto-enabled on `localhost` (Expo tunnel) |

All three consumers initialize services with the same factory calls, differing only in the injected adapter implementations.

## 6.5 Security Implementation Analysis

### 6.5.1 Authentication Defense Depth

The authentication system implements **seven layers of defense**:

| Layer | Mechanism | Attack Mitigated |
|---|---|---|
| 1. Domain Restriction | `@tip.edu.ph` email enforcement + Google OAuth `hd` restriction | Unauthorized registration |
| 2. Password Security | bcrypt (10 salt rounds) + min 8 / max 64 char rules | Brute-force, rainbow table |
| 3. Adaptive reCAPTCHA | Triggered after N failed attempts | Automated credential stuffing |
| 4. Two-Factor Authentication | Email OTP or TOTP (AES-256 encrypted secrets) | Credential compromise |
| 5. Progressive Lockout | `locked_until` timestamp with escalating duration | Persistent brute-force |
| 6. Timing Attack Resistance | Cryptographic random delays on failures | Timing-based credential enumeration |
| 7. Session Anchoring | Per-staff `sid` in Redis validated every request | Session hijacking |

### 6.5.2 OWASP Top 10 Coverage

| OWASP Risk | MDSystem Mitigation |
|---|---|
| A01: Broken Access Control | RBAC with 40+ permissions + branch scoping; `jwtProtect` middleware; `PermissionRoute` guards |
| A02: Cryptographic Failures | bcrypt hashing; AES-256 TOTP encryption; TLS in transit; `JWT_SECRET` / `TOTP_ENCRYPTION_KEY` rotation |
| A03: Injection | Parameterized SQL queries throughout; Joi validation; XSS sanitization |
| A04: Insecure Design | Status-driven workflows prevent invalid state transitions; principle of least privilege |
| A05: Security Misconfiguration | Helmet CSP/HSTS headers; environment-based configuration; no default credentials |
| A06: Vulnerable Components | Regular dependency updates; minimal dependency surface |
| A07: Auth Failures | Multi-layer auth defense (see 6.5.1); login attempt tracking; refresh token reuse detection |
| A08: Software Integrity | Magic-byte file validation; content-type verification; staging area validation |
| A09: Security Logging | Winston daily rotating logs; `UserLoginAttempt` tracking; audit trails in transaction logs |
| A10: SSRF | Chatbot proxy restricted to configured `CHATBOT_URL`; no user-controlled URL resolution |
