# MDSystem system context and agent orchestration

This is the starting point for coordinating changes across MDSystem. It maps the live code paths, identifies shared contracts, and gives the lead agent a workflow for assigning and verifying work. The [documentation index](README.md) links to detailed feature guides. Use the current code, tests, and deployment configuration to resolve discrepancies with older documentation. The root `context.txt` contains a coverage snapshot.

## System and runtime

- **Patient web** is a React and Vite portal for registration, record intake and updates, appointments, medicine requests, health chat, documents, and settings. Start at [App.jsx](../mds-patient/src/App.jsx), [Dashboard.jsx](../mds-patient/src/pages/Dashboard.jsx), and [feature modules](../mds-patient/src/modules).
- **Staff web** is a separate React and Vite portal for patient search, record review, consultations, appointments, inventory, chat, analytics, announcements, notifications, and role administration. Start at [App.jsx](../mds-staff/src/App.jsx), [Dashboard.jsx](../mds-staff/src/pages/Dashboard.jsx), and [feature modules](../mds-staff/src/modules).
- **Patient mobile** is an Expo and React Native TypeScript app. Navigation, screens, and services live under `mds-mobile/src`. It uses the patient backend over an absolute `EXPO_PUBLIC_API_URL` and uses AsyncStorage via the platform adapter. The repo provides native and Expo web entry points. [App.tsx](../mds-mobile/App.tsx) · [Mobile adapter](../mds-mobile/src/core.ts) · [Mobile README](../mds-mobile/README.md)
- **Backend** is one source tree with two Express processes. The patient process defaults to port 3000 and serves the patient SPA build. The staff process defaults to port 3001 and serves the staff SPA build. Both mount REST and domain-specific GraphQL routes, and both initialize Socket.IO. Several medically scoped GraphQL endpoints are mounted on the patient server as well, so trace mount and authorization independently. [Patient server](../Backend/server.js) · [Staff server](../Backend/staff.js)
- **Shared client code** lives in `@mdsystem/core`. It provides API origin handling, Axios behavior, token storage and refresh, Socket.IO helpers, validation, and OAuth and reCAPTCHA helpers. The webs inject browser and Vite behavior and use distinct patient and staff token namespaces. Mobile uses a patient namespace through its own platform adapter. Root npm workspaces cover shared packages and both web apps. Backend has its own package, and mobile has its own package and lockfile with a local dependency on core. [Core package](../packages/core/README.md) · [Patient adapter](../mds-patient/src/packages-core-adapter.js) · [Staff adapter](../mds-staff/src/packages-core-adapter.js) · [Root manifest](../package.json)
- **State and background work** use PostgreSQL for application records and Redis for session and operational state, rate limiting, Socket.IO coordination, and BullMQ queues. The email worker is a separate process. Both portals share the Compose media volume. The e-consultation proxy forwards to the external chatbot configured by `CHATBOT_URL`. [Database adapter](../Backend/config/db.js) · [Redis adapter](../Backend/config/redis.js) · [Sockets](sockets.md) · [Email worker](../Backend/services/email/emailworker.js) · [Chatbot proxy](../Backend/config/middleware/chatbotProxy.js) · [Runtime Compose](../compose.yaml)

Trace the portal adapter and client session handling through the mounted auth and settings routes to the backend session utilities. Access checks also depend on credential status, the account lifecycle, and the applicable session anchor. ## Data, tests, and release boundaries

- **Local runtime.** For frontend development use `npm run dev:patient` or `npm run dev:staff`. Trace the Vite proxy settings when pairing either frontend with an API. The root scripts `npm run start:patient` and `npm run start:staff` launch the Express processes with their configured PostgreSQL and Redis dependencies. The Compose launcher can run the configured stack, including the email worker. Confirm the selected API and datastore targets before exercising write paths. [Patient Vite config](../mds-patient/vite.config.js) · [Staff Vite config](../mds-staff/vite.config.js) · [Compose launcher](../scripts/compose.js) · [Docker guide](DOCKER.md)
- **Initial schema and migrations.** A complete initial PostgreSQL schema and setup SQL must be available at the configured host paths. The Git tree includes incremental migrations, including the custom employee category field and notes columns for medical history and immunization. Inspect the deployed schema revision and migration order before proposing a database change. Treat setup, migrations, and resets as separate operations. [Compose schema setup](../compose.yaml) · [Tracked migrations](../schemas/migrations) · [Docker guide](DOCKER.md)
- **Local checks.** CI uses Node.js 22, `npm ci` at the root, and `npm ci --prefix mds-mobile`. The root install hook handles Backend dependencies. Use `npm test -- --selectProjects <project> --runTestsByPath <test-file>` for a targeted Jest check. Project names are `backend`, `patient`, `staff`, `mobile`, `core`, and `integration`. Use `npm run test:coverage` for the configured coverage gate and `npm run build` for the web builds. For Expo bundle changes, the mobile package provides `npm run --prefix mds-mobile export:all`. An export verifies bundling. Device-specific behavior needs an appropriate device or emulator check. [Root scripts](../package.json) · [Jest config](../jest.config.js) · [Mobile scripts](../mds-mobile/package.json) · [CI](../.github/workflows/ci.yml)
- **Browser checks.** `npm run test:gui` can use configured portal URLs or local Vite previews. Check the target first because the Playwright config loads `.env.e2e` when it exists. `npm run test:e2e:core` and `npm run test:e2e:full` use the disposable Compose harness. Lifecycle and staff-record suites offer mocked projects and local diagnostic scripts. Persistent registration, review, staff decisions, and lifecycle runs can create or alter QA records, so identify the target and use the documented test accounts and workflow for that environment. [Playwright config](../playwright.config.js) · [Disposable Compose](../e2e/compose.yaml) · [E2E guide](PLAYWRIGHT_E2E.md) · [Lifecycle guide](PLAYWRIGHT_LIFECYCLE.md)
- **Release and operations.** The runtime Docker image packages both web builds and supports the separate patient, staff, and email-worker processes. The publish workflow deploys a verified source revision to staging and uses a use-case approval gate before production promotion. The CI workflow for pushes to `deployment` can delete and recreate the Pi use-case PostgreSQL and schema-state volumes. Check the branch, environment, workflow, and authorization before taking an action that can trigger those effects. [Dockerfile](../Dockerfile) · [CI workflow](../.github/workflows/ci.yml) · [Publish workflow](../.github/workflows/publish-and-deploy.yml) · [Deployment guide](CI_CD.md)
- **Configuration and sensitive data.** Start with `.env.example` and the environment variable names in code. Keep secret values, real patient records, account identifiers, credentials, tokens, and private E2E evidence out of shared context. Use synthetic records for cross-agent evidence. Keep external service state and credentials scoped to the environment. [Environment template](../.env.example) · [E2E examples](../e2e/config.example.env) · [Authentication review](AUTHENTICATION_REVIEW.md)
- **Repository boundaries.** `AutoGform/` holds a separate UiPath project and is outside the root npm and Compose runtime. Use `Docs/archive/` and the academic materials for historical context. Generated coverage, local logs, dependency folders, E2E evidence, and app builds are separate from the source paths above. ## How the lead agent coordinates work

1. **Frame the outcome.** Record the requested behavior, actor, entry point, acceptance criteria, and environment. Trace the current flow and identify shared files and boundaries before assigning work.
2. **Agree on contracts.** For a shared change, capture the endpoint, GraphQL fields or event payload, permission and ownership rules, state transition, migration need, and behavior for existing records. Name an owner for each shared contract and note any consumer that depends on it.
3. **Delegate only where ownership is clear.** Split work by touched surface such as backend and data, patient web, staff web, mobile and core, or independent verification. Assign one writer per file set and give each agent the paths, base revision, required checks, and dependencies. Keep dependent edits sequential until the contract is agreed. Keep integration and cross-surface decisions with the lead agent.
4. **Integrate and verify.** Review each patch against actual callers, preserve unrelated workspace changes, and resolve discrepancies before running the integrated checks. Verify successful behavior and affected denial or failure paths. For workflow changes, verify state readback on the receiving surface and relevant notifications or document effects. Use disposable or synthetic data for this evidence.
5. **Close with evidence.** Report what changed, each check's result, and any blocked or unverified environment-dependent behavior. Record any required rollout order or operational follow-up with its target and dependency.

Use this handoff format for each assignment and result.

```text
Outcome and acceptance criteria
Owner and owned files
Base revision and relevant code paths
Shared contracts and dependencies
Environment and permitted side effects
Required checks and expected evidence
Return: changed files, checks and results, unresolved issues
```

For example, an EMR profile field starts with the data and API owner verifying storage compatibility and the GraphQL contract. The patient web, mobile, and staff owners then check form submission, old records, review and readback where each surface consumes the field. The lead checks that the migration and app changes can be rolled out in the required order and verifies the integrated flow with a synthetic patient.
