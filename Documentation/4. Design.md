### 4.1.2 Dual-Server Architecture

MDSystem operates as two independent Express 5 server processes sharing a common codebase:

| Server | Entry Point | Port | Serves | JWT Role Enforcement |
|---|---|---|---|---|
| Patient Server | `server.js` | 3000 (configurable via `PATIENT_PORT`) | Patient web portal (`mds-patient/dist`), patient mobile app, patient-scoped API routes | `jwtProtect('patient')` |
| Staff Server | `staff.js` | 3001 (configurable via `MEDICAL_PORT`) | Staff web portal (`mds-staff/dist`), staff-scoped API routes | `jwtProtect('medical')` + session anchor validation |

Both servers instantiate their own Socket.IO server connected to the same Redis adapter, enabling real-time events emitted on one server to be delivered to clients connected to the other. This architecture allows independent scaling and deployment of patient-facing and staff-facing resources.

The system employs a **hybrid REST + GraphQL** API architecture:

**GraphQL Endpoints** (primary for complex CRUD):
- `/emr/patient` and `/emr/medical` — Electronic Medical Records

## 4.2 Database Design

### 4.2.1 Entity-Relationship Overview

The PostgreSQL database contains **60+ tables** organized into the following functional domains:

**User Management Domain:**
- `UserCredentials` — Authentication credentials (email, password hash, identity, credential status, TOTP settings, data consent)
- `UsersPersonal` — Personal information (name, DOB, sex, civil status, contact, address)
- `UsersPersonalLog` — Audit log of personal information changes
- `UsersPreferences` — JSONB user preferences for notifications and UI settings
- `UserLoginAttempt` — Login attempt tracking (IP, timestamp, success/failure)
- `profileRecord` — Polymorphic profile type discriminator
- `student_profile` — Student-specific data (program, year level)
- `employee_profile` — Employee-specific data (department, role, position)

**Patient Domain:**
- `Patients` — Patient records linked to `UserCredentials`
- `patientUpdateLog` — EMR update ticket tracking with status workflow (InProgress → Pending → Approved/Revision/Rejected)

**Medical Record Domain:**
- `MedicalHistory` — Chronic conditions, hospitalizations, operations (linked to `DomainTypeCatalog`)
- `DentalHistory` — Oral health history, cleaning frequency, tooth sensitivity
- `DentalRecord` — Per-tooth condition grading using 13-legend dental chart
- `Allergy` / `AllergenCatalog` — Allergy records with type, severity, status
- `Immunization` / `ImmunizationRecord` — Vaccination records with dose tracking
- `VitalSigns` — Blood pressure, heart rate, temperature, height, weight, BMI
- `LifestyleAssessment` — Smoking, alcohol, drug use, exercise frequency, vaping
- `ObGyneRecord` — OB-GYN history for female patients
- `EmergencyContact` / `EmergencyNumber` — Dual emergency contact system
- `DomainTypeCatalog` — Shared catalog for medical conditions, medications, immunizations, dental procedures

**Consultation Domain:**
- `Consultation` — Consultation sessions (mode: Onsite/Virtual, type: Medical/Dental, status workflow)
- `ConsultationOutcome` — Clinical findings (complaints, PE findings, treatments)
- `ConsultationDiagnosis` — ICD-10 coded diagnoses (8 diagnosis type classifications)
- `ICDLookup` — Cached WHO ICD-11 API responses for offline-first code resolution

**Appointment Domain:**
- `SlotScheduler` — Scheduling templates (location, session, capacity, weekday availability)
- `ScheduleDateEntity` — Individual date slots with custom capacity overrides
- `SlotCustomDateEntry` — Include/exclude date overrides
- `patientSlot` — Individual patient appointment bookings (9-state status machine)
- `scheduleRequirement` / `patientScheduleRequirement` — Appointment file requirements (e.g., lab results for OJT)

**Health Chat Domain:**
- `HealthChatConsultation` — Chat tickets (status: Open → Ongoing → Closed/Expired)
- `HealthChatPrompts` — Messages (type: text/file/system) with foreign key to assignee and patient

**Medical Inventory Domain:**
- `MedicalItems` — Master item catalog (Medicine or Supply category)
- `MedicineBatch` — Medicine batch tracking (batch number, expiry, location, supplier, stock)
- `SupplyBatch` — Supply batch tracking (batch number, expiry, location, supplier)
- `MedicineEntity` / `SupplyEntity` — Individual dispensed unit records
- `MedicineTransactionLog` / `SupplyTransactionLog` — Audit trail (Issue, Return, Adjust actions)
- `MedicineRequestLog` — Patient medicine requests (5-state status machine)
- `MedicineRequestEntity` — Requested item quantities per request
- `Prescription` / `PrescriptionItem` — Staff-issued prescriptions

**Document Domain:**
- `patientRawDocument` — Patient document uploads (status: Requested → Pending → Recorded → Archived)
- `rawDocumentTag` — Document type tags defining required documents per role
- `PatientDocuments` — Generated documents (certificates, prescriptions, reports)

**Staff & RBAC Domain:**
- `MedicalPersonnel` — Staff records (role, title, designation, active status)
- `rolesMap` — Personnel-to-permission mapping with branch scoping
- `rolesTable` — Permission definitions (40+ permission keys)
- `rolesTemplate` / `rolesTemplateMap` — Reusable permission templates for role provisioning

**Communication Domain:**
- `Announcement` — Branch-scoped announcements with pubmat file support
- `Notification` — System notifications with delivery tracking

### 4.2.3 Data Access Pattern

The system uses **raw parameterized SQL** via the `pg` (node-postgres) connection pool — no ORM is employed. This design decision provides:

- Full control over query optimization and join strategies
- Direct access to PostgreSQL-specific features (JSONB, custom enums, CTEs, window functions)
- Reduced abstraction overhead for complex multi-table analytics queries
- Controlled foreign key and unique constraint violation handling via `queryControlled()`

## 4.3 Authentication and Security Design

### 4.3.1 Authentication Flow

```
┌──────────┐     POST /auth/login      ┌──────────────────┐
│  Client   ├──────────────────────────►│  Validate Creds  │
│           │                           │  + Adaptive       │
│           │      LoginKey             │  reCAPTCHA        │
│           │◄──────────────────────────┤                   │
│           │                           └──────────────────┘
│           │     POST /auth/email/2fa
│           │     (OTP or TOTP code)    ┌──────────────────┐
│           ├──────────────────────────►│  Verify 2FA       │
│           │                           │  Issue JWT Pair    │
│           │  { accessToken,           │  Store Refresh in  │
│           │    refreshToken }         │  Redis             │
│           │◄──────────────────────────┤                   │
└──────────┘                            └──────────────────┘
```

**JWT Token Architecture:**
- **Access Token:** Short-lived, signed with `JWT_SECRET`, audience `mdsystem-app`, issuer `mdsystem-auth`. Payload includes `userId`, `email`, `role`, `branch`, and staff-specific `sid` (session anchor).
- **Refresh Token:** Format `userId:deviceId:refreshToken` where `refreshToken` is a UUID. Stored in Redis with full session metadata. Enables token rotation with reuse detection.
- **Staff Session Anchoring:** Medical role tokens include a `sid` validated against Redis on every request, ensuring only one active session per staff member per device.

### 4.3.3 Security Measures Summary

| Layer | Mechanism |
|---|---|
| **Transport** | HTTPS/TLS, Helmet security headers (CSP, HSTS, X-Frame-Options) |
| **Authentication** | bcrypt password hashing (10 salt rounds), JWT with RS256-equivalent security |
| **2FA** | RFC 6238 TOTP with AES-256 encrypted secret storage + email OTP fallback |
| **OAuth** | Google Identity Services restricted to `@tip.edu.ph` hosted domain |
| **Bot Protection** | Adaptive reCAPTCHA v2 (triggered after failed login threshold) |
| **Rate Limiting** | Redis-backed IP rate limiting with profile-based configs (patient vs staff) |
| **Lockout** | Progressive account lockout after repeated failures with `locked_until` timestamp |
| **Timing Safety** | Cryptographically random delays on auth failures; timing-safe comparison for secrets |
| **Input Validation** | Joi schema validation, XSS sanitization, institutional email pattern enforcement |
| **File Security** | Magic-byte validation (JPEG, PNG, WebP, PDF, MP4, MOV), `safeResolve()` path traversal protection |
| **Session** | Staff session anchor (`sid`) in Redis, single active session enforcement |
| **Consent** | Versioned Data Privacy Act consent with timestamp recording |

## 4.5 Real-Time Communication Design

### 4.5.1 Socket.IO Room Hierarchy

```
Socket.IO Server (Redis Adapter for cross-server pub/sub)
│
├─ Per-User Rooms
│  └─ user:{userId}  ← personal notifications, force-logout
│
├─ Role Rooms
│  ├─ role:patient   ← patient-wide broadcasts
│  └─ role:medical   ← staff-wide broadcasts
│
├─ Health Chat Rooms
│  └─ healthchat:{chatId}  ← per-conversation messages, typing
│
├─ Branch-Scoped Rooms (staff join based on permissions)
│  ├─ branch:{location}:appointments  ← appointment events
│  ├─ branch:{location}:inventory     ← medicine/inventory events
│  └─ {branch}::staff                 ← EMR update ticket events
│
└─ Admin Rooms
   └─ admin:notification  ← system-wide admin alerts
```

### 4.5.2 Offline Notification Flow

```
  Client Disconnected                      Client Reconnects
        │                                        │
  ┌─────▼─────┐                            ┌─────▼─────┐
  │ Event      │   Redis LPUSH             │ Socket    │
  │ emitted    ├──►notif:pending:{userId}  │ connected │
  │            │                           │           │
  └────────────┘                           └─────┬─────┘
```

## 4.6 Key Workflow Designs

### 4.6.1 EMR Update Approval Workflow

```
Patient submits update (Medical/Dental/Both scope)
       │
       ▼
  ┌──────────────┐       ┌──────────────┐
  │  InProgress   │──────►│   Pending     │  (auto-advance on submit)
  └──────────────┘       └──────┬───────┘
                                │
                    ┌───────────┼───────────┐
                    ▼           ▼           ▼
              ┌──────────┐ ┌─────────┐ ┌──────────┐
              │ Approved  │ │Revision │ │ Rejected │
              │ (final)   │ │Requested│ │ (final)  │
              └──────────┘ └────┬────┘ └──────────┘
                                │
                                ▼
                        ┌──────────────┐
                        │  Revision     │
                        │  Submitted    │──► (returns to Pending)
                        └──────────────┘

  Additional terminal states: Cancelled (by patient), Expired (7-day timeout)
```

### 4.6.2 Consultation Lifecycle

```
Staff creates consultation for patient
       │
       ▼
  ┌──────────────┐     Staff adds outcomes     ┌──────────────┐
  │   Created     │────────────────────────────►│     Open      │
  └──────────────┘                              └──────┬───────┘
                                                       │
                                          ┌────────────┼────────────┐
                                          ▼            ▼            ▼
                                    ┌──────────┐ ┌──────────┐ ┌──────────┐
                                    │Completed │ │ Referred │ │Monitored │
                                    └──────────┘ └──────────┘ └──────┬───┘
                                                                     │
                                                              ┌──────▼───┐
                                                              │  ReOpen   │
                                                              └──────────┘
  
  Each outcome contains: Complaints, PE Findings, Treatments
  Each outcome links to: ICD-10 Diagnoses (Primary, Secondary, Differential, etc.)
```

### 4.6.3 Appointment Scheduling Flow

```
                    Staff configures SlotScheduler
                    (location, session, capacity, weekdays)
                              │
                              ▼
Patient views available dates/sessions ◄── ScheduleDateEntity
       │                                    (auto-generated or custom)
       ▼
  ┌──────────────┐
  │   Pending     │  ← Patient books slot
  └──────┬───────┘
         │
    ┌────┼────────────────────────┐
    ▼    ▼                        ▼
┌────────┐ ┌──────────┐    ┌──────────┐
│Scheduled│ │ Rejected │    │ Expired  │ (auto after timeout)
└───┬────┘ └──────────┘    └──────────┘
    │
    ├──► InProgress ──► Completed
    ├──► NoShow
    ├──► CancelledByPatient
    └──► CancelledByMedical
```

### 4.6.4 Medicine Request and Dispensing Flow

```
Patient submits medicine request (items + quantities + location)
       │
       ▼
  ┌──────────────┐
  │   Pending     │  → Socket event: medicine:request:new
  └──────┬───────┘
         │
    ┌────┼────────────────────┐
    ▼    ▼                    ▼
┌────────┐ ┌──────────┐ ┌──────────┐
│Approved │ │ Rejected │ │Cancelled │ (by patient)
│(→ stock │ └──────────┘ └──────────┘
│reserved)│
└───┬────┘
    │
    ▼
┌────────────┐
│ Completed   │  ← Staff physically dispenses
│ (entities   │     MedicineEntity created per unit
│  created)   │     TransactionLog recorded
└────────────┘
```
